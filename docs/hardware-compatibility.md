# Hardware compatibility

## Ubuntu 24.04+ / PipeWire

- The Linux PipeWire backend and live `record-test` path compile in Ubuntu 24.04 CI and in a local Ubuntu 24.04 WSL environment.
- PipeWire default-source discovery was exercised in WSL on 2026-10-03 using an isolated PipeWire/WirePlumber session, a synthetic null source, and the session's `default.audio.source` metadata. `clearmic-cli devices` marked the matching source as default. This verifies the metadata-to-device mapping only; it does not count as physical microphone or audio-routing validation.
- On 2026-10-03, an independent PipeWire daemon was started from a temporary copy of `minimal.conf` with PipeWire's `audiotestsrc` plugin. `clearmic-cli devices` discovered the test source, and `clearmic-cli serve <source-id>` published a node named `ClearMic Virtual Microphone` while the service ran. The source was synthetic and produced zero RMS in this WSL setup; this verifies source discovery and virtual-node registration only, not non-silent processed audio, physical capture, or consumption by another application. The temporary daemon was stopped after the check.
- Linux device recovery was exercised in the same isolated PipeWire/Xvfb setup with a stale microphone ID in a temporary `settings.ini`. On launch, the GTK panel selected the available default source and replaced the stale ID in settings. This verifies fallback selection and persistence, not recovery from physical hotplug or audible capture.
- On 2026-10-03, after installing the documented Linux development packages in WSL, the full GTK/PipeWire build completed, all 11 CTest cases passed, and `packaging/linux/build-deb.sh` produced `clearmic_0.1.0_amd64.deb`. Installing that package with apt resolved its declared runtime dependencies; `clearmic-cli --help`, desktop-entry validation, and an Xvfb launch found the ClearMic window. Sending the window's advertised `WM_DELETE_WINDOW` protocol closed it cleanly with exit code 0 and no GTK/GDK warnings. An earlier `xdotool windowclose` smoke emitted teardown warnings because it did not exercise this protocol correctly; the CI smoke now sends the protocol directly. This validates package startup and window shutdown under Xvfb, not physical audio or PipeWire routing.
- The GitHub Actions run for commit `9cb38da` completed successfully on Windows and Ubuntu on 2026-10-03. Both platform builds and CTest jobs passed; the workflow also built, installed, registered, and removed the Windows MSI, launched the packaged Linux desktop entry under Xvfb, and uploaded Windows MSI and Ubuntu `.deb` artifacts. This is packaging/launcher validation in CI, not full physical-device or audible-route validation.
- The WSL environment has no connected PipeWire microphone source. Enumeration reports no input device; the capture command rejects this state instead of producing a misleading silent recording. No physical device audio was captured and no hardware compatibility is claimed from this run.
- The Linux backend now maps a PipeWire Bluetooth address to BlueZ's reported battery percentage when available. WSL does not expose a BlueZ system bus or connected Bluetooth microphone, so this telemetry path has not been validated against physical hardware here.
- Linux additionally checks UPower for an accessory battery object with the exact PipeWire Bluetooth address, allowing real charging-state telemetry where exposed. The current WSL environment has neither an active UPower system service nor a Bluetooth microphone; this UPower path is unit-tested but not physically validated here.
- On a desktop session with PipeWire, run `clearmic-cli devices` and `clearmic-cli record-test 5 original.wav processed.wav [device-id]` to validate an actual source. The current WSL environment cannot perform this step.

## Development machine: Windows 11

### Current Windows audio endpoints

- Input endpoint observed: `Microfone (Realtek(R) Audio)`.
- Output endpoint observed: `Altofalantes (Realtek(R) Audio)`.
- A fresh native MinGW-built `clearmic-cli devices` run on 2026-10-03 again listed the Realtek endpoint as the only selectable microphone (48 kHz, two channels). The supplemental inventory also listed `EDIFIER TWS1 Pro 2 Hands-Free AG` and `WF-C710N Hands-Free AG` as non-selectable Bluetooth audio functions, not capture endpoints; this CLI output included no battery values for those functions. The matching `clearmic-core-tests.exe` built by MinGW ran natively on Windows and exited with code 0.
- A newer native `clearmic-cli devices` inventory on 2026-10-03 still found the Realtek endpoint as the only selectable input and also found a non-selectable Bluetooth Hands-Free HF function. A read-only enumeration of `GUID_DEVINTERFACE_BATTERY` returned only the laptop's `ACPI\\PNP0C0A\\1` interface. The Realtek endpoint's ContainerId and each PnP ancestor reported the sentinel `{00000000-0000-0000-FFFF-FFFFFFFFFFFF}`, so this host does not provide a trustworthy container-based battery association for the microphone. The native Battery Class backend probe showed unavailable for all current selectable and supplemental input entries; it did not attribute the laptop battery to any audio device.
- A fresh native run on 2026-10-03 now reports the Realtek microphone as connected and the paired WF-C710N, EDIFIER, and `VinRamalho` Bluetooth Hands-Free functions as disconnected. This uses Windows' classic Bluetooth device inventory `fConnected` value matched to the remote address in each profile instance ID. Those functions remain non-selectable because no corresponding WASAPI capture endpoints are active. This corrects an earlier status that treated a present, problem-free PnP function as connected.
- The WF-C710N appears as a Bluetooth PnP device and as `WF-C710N Hands-Free` / `WF-C710N` MEDIA functions under one Windows device container. It does not currently appear as an active `AudioEndpoint` capture device, so ClearMic cannot select it through WASAPI at this time.
- The CLI's supplemental Bluetooth inventory lists paired Bluetooth audio functions separately from selectable WASAPI endpoints. Earlier versions treated a present PnP devnode with no driver error as connected; that only established installation, not a live Bluetooth connection. The backend now uses Windows Bluetooth connection state when it can match the remote address, and otherwise reports unknown.
- A native Windows `record-test 3` invocation selected the Realtek default endpoint, completed WASAPI capture, and created valid 48 kHz mono WAVs with 144,000 frames each.
- The captured 3-second sample was all zero (peak 0, RMS 0), so this run proves endpoint opening, buffer flow, and WAV output but does not verify an audible microphone signal or enhancement quality. The microphone may have been muted or no sound was present during the test.
- A repeat 3-second capture on 2026-10-03 with the current Windows cross-build again completed successfully and wrote both local A/B WAVs (288,044 bytes each, 48 kHz mono PCM16, 144,000 samples). Both original and processed files had peak 0, RMS 0, and no nonzero or clipped samples. This reconfirms the WASAPI capture/file path only; no audible input or processing quality was measured.
- A further five-second `record-test` selected the Realtek endpoint by ID and wrote 48 kHz mono PCM16 files with 240,000 frames each. WASAPI reported a 4,800-frame capture buffer and no stream latency; the shared DSP processed the sample in 90.3 ms wall time. Both original and processed audio were silent (peak 0, RMS 0), so this confirms capture and A/B file processing only, not microphone signal or enhancement quality.
- A fresh five-second capture after the shared DSP changes again wrote 240,000-frame WAVs. Both original and processed samples measured peak 0 and RMS 0; WASAPI reported a 4,800-frame buffer, latency unavailable, and 93.0 ms A/B DSP compute time. The real endpoint continues to provide no audible signal in this validation, so voice quality and the real-microphone noise gate remain unverified.
- The updated native CLI was then run for two seconds and reported input/processed RMS at 0.00%, explicitly warning that little or no microphone signal was detected. WASAPI opened the endpoint with a 4,800-frame buffer, latency unavailable, and 49.8 ms A/B DSP compute time. This confirms the new no-signal diagnostic against the current device; it still does not evaluate voice processing quality.
- The desktop's idle `IAudioMeterInformation` query on the Realtek capture endpoint succeeded and showed the Input level meter as available, with a current peak of 0/100. This agrees with the zero-sample WASAPI capture above and verifies access to Windows' endpoint meter without ClearMic opening a capture stream. A positive meter response to audible speech remains unverified.
- Repeat `clearmic-cli record-test 5 original.wav processed.wav [device-id]` while speaking into the device, then compare both files. Omit the ID to use the Windows default microphone.
- The Windows panel now enumerates playback endpoints, saves an explicitly selected output, and exposes a start/stop live WASAPI processing route to that endpoint. The implementation uses 48 kHz mono PCM16 with shared-mode conversion, the Windows engine-selected event period, and a bounded queue. The Windows CI and MinGW cross-builds verify compilation, but the panel route has not yet been exercised on the Windows host with a compatible virtual cable.
- While the route is active, the panel reports capture/render buffer capacities, each `IAudioClient::GetStreamLatency` value when Windows provides one, and the maximum measured DSP processing time for a capture packet. An unavailable stream-latency value is shown as unavailable; the displayed buffer sizes and DSP duration do not establish total end-to-end latency.
- No virtual-audio cable driver was found or installed for this validation. The observed Realtek playback endpoint is a physical speaker and was not used for live routing, to avoid acoustic feedback. Therefore the Windows processed microphone is not yet verified in a separate consumer application.

### Sony WF-C710N

- Present as a Bluetooth PnP device. Its AVRCP service IDs report vendor `054C` and product `0F8B`.
- Windows exposes WF-C710N Hands-Free and media PnP functions, but no active WASAPI `AudioEndpoint` capture endpoint was listed during inspection.
- A GATT Battery Service (`0x180F`) was present for a different paired BLE device (`5FA9BC30D18D`), not for the WF-C710N. This does not establish battery telemetry for the headset.
- Windows `root/wmi:BatteryStatus` currently reports only `ACPI\\PNP0C0A\\1_0` (the system battery). No battery WMI instance was associated with the WF-C710N device container, so its charge and charging state remain unknown.

### USB wireless device

- Windows reports a connected composite USB device with bus description `Wireless Device`, VID `3151`, PID `3020`, revision `0002`.
- It exposes `MI_00` and `MI_01` interfaces. PnP classifies both as HID interfaces; no USB Audio interface or corresponding microphone endpoint is currently visible.
- PnP shows an active composite receiver (`USB\\VID_3151&PID_3020`, revision `0002`) with `MI_00` and `MI_01`; the `MI_01` children include mouse (`UP:0001/U:0002`), system control (`UP:0001/U:0080`), consumer control (`UP:000C/U:0001`), and vendor-defined (`UP:FF00/U:000E`) HID collections. They share container `{999EC788-C3EC-5F0C-B470-BA9DC2EEC329}`.
- The collections have no PnP problem code, and Windows exposes only generic `DEVPKEY_Device_PowerData`; that is OS power-management metadata, not a device battery percentage or charging report.
- Read-only `HidD_GetPreparsedData` / `HidP_GetCaps` inspection of the vendor collection found a 32-byte input report and a 32-byte output report, both report ID `0xBA` with 31 eight-bit vendor values; no feature reports are declared. A GET_INPUT_REPORT returned 32 zero bytes in three reads spaced five seconds apart, and a 10-second passive overlapped input read received no reports. The declared output report was not sent. No battery semantics or changing telemetry were observed. Transmitter/receiver battery availability remains **unknown** because the wireless transmitter was not confirmed active during this inspection; no telemetry is shown or inferred.

Battery and transmitter/receiver values for the WF-C710N and USB wireless device remain unknown. The USB investigation includes parsed HID capabilities and read-only input reports, but the transmitter was not confirmed active and the vendor report semantics remain unknown. Sony headset capture, charging status, actual audio quality, and virtual-microphone routing have not been tested with actual sound or an application consumer.
