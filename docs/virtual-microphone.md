# Virtual microphone investigation

## Linux

The Linux CLI can publish a PipeWire source fed by the live processing chain:

```bash
./build/clearmic-cli serve [pipewire-source-id] [natural|meeting|strong] [processing switches]
```

Processing switches include `--noise-suppression=on|off`, `--noise-gate=on|off`, `--automatic-gain=on|off`, and `--compressor=on|off`.

The command opens the selected microphone (or PipeWire's default source), processes mono 48 kHz PCM16 in the PipeWire capture callback, and publishes the result as **ClearMic Virtual Microphone**. The process must remain running. Ctrl+C stops it. A bounded single-producer/single-consumer queue separates the capture and source callbacks. If the consumer falls behind, the producer advances the oldest-sample cursor with compare-and-swap and drops stale samples; atomic sample slots let a concurrent consumer detect that cursor change and emit silence for that block instead of returning partially overwritten audio. This keeps the queue bounded and favors recent speech. The service reports processed duration, capture overruns, source underruns, maximum DSP time per capture callback, and that maximum as a percentage of the corresponding audio packet duration. When available, the panel also shows PipeWire's capture and source stream delay, queued, and buffered values separately; these backend-reported values are not summed with DSP time into an end-to-end route measurement. Missing stream timing is reported as unavailable. The DSP timing is measured inside the callback but emitted by a once-per-second timer; it does not represent capture-to-application latency. If the service exits unexpectedly, the panel refreshes the device list and retries with a bounded backoff using the selected available microphone, falling back to the current default when the previous source disappeared; Stop cancels retries. Optional tray mode keeps the panel available after its window closes and provides an action that starts or stops enhancement based on the current service state.

## Windows

WASAPI capture enumeration does not create a microphone endpoint. WASAPI loopback captures rendered system audio, so it is useful as a possible AEC reference but cannot make ClearMic's processed microphone selectable by other applications ([Microsoft loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)).

The Windows panel discovers active input and playback endpoints. It can continuously capture the selected WASAPI microphone, apply the shared DSP chain, and render processed mono 48 kHz PCM16 to an explicitly selected playback endpoint. Select the playback/input side of a virtual audio cable; other applications then select that cable's paired recording/output side as their microphone. The panel recognizes endpoints by directional names such as VB-CABLE's `CABLE Input` and `CABLE Output` (as named in the [vendor manual](https://vb-audio.com/Cable/VBCABLE_ReferenceManual.pdf)); it hides the cable's recording side from the source-microphone list to avoid routing the processed stream back into ClearMic. Before enabling the route, it also checks for an active capture endpoint whose name contains the corresponding output name. The MikeTheTech driver's published `Virtual Audio Driver` and `Virtual Mic Driver` names are also recognized and paired. This prevents starting with an incomplete pair, but remains a name-based check: custom-renamed devices may not be recognized, and matching names cannot prove that a driver transports audio correctly.

When no recognized cable is present, the Windows panel offers a **Download VB-CABLE** shortcut to VB-Audio's official product page. VB-CABLE is an optional third-party donationware driver, not bundled with ClearMic. The vendor's documented flow is to extract its download, run the setup as administrator, and restart Windows; the panel tells the user these requirements ([installation manual](https://vb-audio.com/Cable/VBCABLE_ReferenceManual.pdf)).

On 2026-10-03, the current official Windows package (`VBCABLE_Driver_Pack45.zip`) was downloaded from VB-Audio and inspected locally. Its SHA-256 was `B950E39F01AF1D04EA623C8F6D8EB9B6EA5C477C637295FABF20631C85116BFB`; Authenticode verification returned `Valid` for the x64 setup executable and the Windows 10 x64 driver catalog. Using the Microsoft Windows SDK BuildTools 10.0.28000.2705 `signtool.exe` (SHA-256 `D6C04707C59A67FCE9FA4BB5FE76C79445B60E1E326D8B500A2F2BA8707C590A`), both `signtool verify /kp /v /c vbaudio_cable64_win10.cat vbaudio_cable64_win10.sys` and `signtool verify /kp /v vbaudio_cable64_win10.cat` succeeded on this Windows 11 development host. The verified chain ends in Microsoft Root Certificate Authority 2010 through Microsoft Windows Third Party Component CA 2014 to Microsoft Windows Hardware Compatibility Publisher; the package signature was timestamped 2024-10-08. This is evidence that the selected x64 catalog/driver pair passes this host's SignTool kernel-policy verification; it is not a substitute for installation and loopback testing with Secure Boot and Memory Integrity enabled. The vendor's [current distribution page](https://vb-audio.com/Services/licensing.htm) says the single VB-CABLE package may be distributed or embedded when users can identify VB-Audio as its origin and can donate/pay for a license; it excludes professional deployments where users cannot pay. The `readme.txt` inside Pack45 separately says the package may be copied and distributed *as-is* but may not be integrated into another software installation procedure without the author's agreement. These statements do not establish that embedding Pack45 in ClearMic's MSI is authorized under the package-specific condition. ClearMic therefore does not bundle or silently install it and continues to send users to the official source. No files from the vendor package were copied into the repository or installed.

The live stream uses event-driven WASAPI shared-mode clients with Windows sample-rate/channel conversion, engine-selected default buffering, preallocated processing/render buffers, and a bounded 4096-sample queue. Queue overflow stops the route with an error rather than allowing unbounded latency. If a disconnected endpoint stops signaling events, the worker checks both WASAPI clients on its one-second wait timeout; a detected invalid endpoint ends routing with an input- or output-specific message, after which the panel refreshes the device lists. The UI provides explicit start/stop, updates input/processed RMS meters from the capture thread at an 80 ms UI interval, and keeps device/processing selections locked while routing. When a tray icon is available, closing the panel during a live route hides it while processing continues; the tray menu can reopen the panel, stop routing, or quit. The 10 ms DSP frame and engine-selected buffer are not an end-to-end latency measurement; hot-unplug recovery, latency, underrun behavior, and virtual-cable compatibility still need native Windows hardware validation. The MSI does not include a virtual-audio driver.

Microsoft's [SYSVAD sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-driver-samples/sysvad-virtual-audio-device-driver-sample/) demonstrates a WDM virtual audio device driver. A user-mode APO can process streams in the Windows audio engine, but it is packaged and registered with an audio driver and does not independently create the virtual capture endpoint ([APO architecture](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/audio-processing-object-architecture)).

Any bundled Windows implementation therefore needs a virtual capture endpoint (or a licensed, redistributable third-party endpoint), a documented installation and update path, and a signed driver package where a kernel driver is used ([driver signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/driver-signing), [public release signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/signing-a-driver-for-public-release)). ClearMic has not selected or bundled a driver and does not create its own Windows virtual microphone; the MSI must not imply otherwise. The current live playback route can feed a separately installed compatible cable endpoint.

### Candidate review (2026-10)

The [Virtual Audio Driver by MikeTheTech](https://github.com/VirtualDrivers/Virtual-Audio-Driver) advertises Windows 10/11 virtual speaker and microphone endpoints. Its repository lists its own code under MIT and SYSVAD-derived portions under MS-PL in its [third-party notices](https://github.com/VirtualDrivers/Virtual-Audio-Driver/blob/main/THIRD_PARTY_NOTICES.md). GitHub currently publishes a [signed 25.7.14 release](https://github.com/VirtualDrivers/Virtual-Audio-Driver/releases/tag/25.7.14) containing `virtualaudiodriver.cat`, `VirtualAudioDriver.inf`, and `VirtualAudioDriver.sys`. I downloaded its ZIP read-only on 2026-10-03; SHA-256 was `DD10560994DE65A7E587FB8B93C0D7E9838292D9C3566A0976C2786D727292BD`, and Windows Authenticode verification returned `Valid` for the catalog and driver, both signed by SignPath Foundation. Its INF targets `NTamd64.10.0...22000`, which includes supported Windows 11 builds but not Windows 10. The upstream README currently has a beta warning that test signing must be enabled. On this host, Microsoft Windows SDK BuildTools 10.0.28000.2705 `signtool.exe` failed both `signtool verify /kp /v /c virtualaudiodriver.cat VirtualAudioDriver.sys` and `signtool verify /kp /v virtualaudiodriver.cat` with `A certificate chain processed, but terminated in a root certificate which is not trusted by the trust provider`; the reported chain ends at GlobalSign Code Signing Root R45 via GlobalSign GCC R45 CodeSigning CA 2020 and SignPath Foundation. Thus its generic Authenticode `Valid` result does not mean it passes this host's kernel-policy verification. Do not bundle or stage this candidate unless a Microsoft-trusted production-signed package passes `/kp` and a normal secured-host install is validated. Microsoft's [kernel driver signing guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/driver-signing) describes the signing requirements for loading kernel-mode drivers. A related [Virtual Driver Control](https://github.com/VirtualDrivers/Virtual-Driver-Control/blob/main/VirtualDriverControl/README.md) advertises checksum/signer checks plus `pnputil` and SetupAPI install/uninstall, and routes audio through the driver's virtual speaker to its virtual microphone; this may fit ClearMic's existing WASAPI route, but does not resolve kernel trust or establish that ClearMic can maintain its lifecycle safely. The driver README offers named-pipe/shared-memory integration only as a separately quoted custom build, so ClearMic would rely on ordinary WASAPI endpoint routing instead.

The current development host runs Windows 11 build 26200 with virtualization-based security and Memory Integrity active. Querying Secure Boot state was denied without elevated privileges. Neither the MikeTheTech driver nor VB-CABLE is installed; both were inspected read-only. MikeTheTech fails `signtool verify /kp` on this host and is not a production candidate in its current signed release. VB-CABLE Pack45's selected Windows 10 x64 catalog/driver pair passes `/kp`, but its package-specific license prohibits integrating it into another software installation procedure without the author's agreement, so ClearMic must continue to direct users to VB-Audio's official download. The next evaluation is normal installation of VB-CABLE on Windows 11 with Secure Boot and Memory Integrity enabled, followed by non-silent audio routing through ClearMic to a separate capture application and measurement of end-to-end latency and endpoint restart recovery. No test-signing mode or platform-security change is acceptable for this validation.

The [Microsoft SYSVAD sample](https://github.com/microsoft/Windows-driver-samples/tree/main/audio/sysvad) remains a reference for WDM/WaveRT endpoint implementation, not a drop-in ClearMic output: it demonstrates a virtual device and sample topologies, but ClearMic would still have to implement and maintain the audio data bridge, package/sign the driver, and pass Windows driver validation. An APO alone also does not create a capture endpoint.

Next evaluation must establish, against a real Windows 11 machine with Secure Boot and Memory Integrity enabled: whether the 25.7.14 release installs under the normal driver-signing policy; whether its virtual speaker and microphone endpoints appear and pass non-silent audio through ClearMic's existing WASAPI route; and whether signed-package verification, consented UAC install, restart handling, and reliable uninstall/upgrade can be implemented from the companion installer's documented flow. Measure capture-to-virtual-mic latency and recovery on endpoint restart. Do not enable test signing, disable platform security, or distribute a driver until these criteria have a supported solution.

### Implementation paths to evaluate

- Adapt the Microsoft SYSVAD sample and maintain a ClearMic virtual capture driver. This offers control over the endpoint and format negotiation, but creates ongoing kernel-driver maintenance, signing, release, and Windows-version compatibility work.
- Integrate a third-party virtual audio driver only after confirming its license permits redistribution, installation, updates, and the intended commercial/open-source use. A technical sample or source-available driver is not automatically safe to bundle.
- Keep a user-mode APO as a possible later effect path if ClearMic needs to process audio in the Windows system pipeline. An APO alone does not provide the virtual microphone endpoint.

The next Windows architecture milestone is to validate the published candidate's kernel signing and secured-host installation, then verify that a separate capture application can enumerate and receive processed audio from its virtual microphone. Until that evidence exists, the project will not bundle a driver or present the Windows MSI as providing a virtual microphone.

## Current status

Linux's `serve` command publishes the PipeWire source and a repeatable isolated WSL test has captured non-silent audio through a `pw-cat` consumer after correcting the source callback scheduling. That synthetic 440 Hz test verifies transport, not speech enhancement or routing in a native desktop application. Windows still has no ClearMic virtual endpoint.
